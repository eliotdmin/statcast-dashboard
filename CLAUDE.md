# Working agreements for this repo

**Read these first, in this order:**

1. `DECISIONS.md` — why the project is built this way. Read before changing an
   approach, so a settled decision is reversed deliberately rather than by
   accident.
2. `FINDINGS.md` — what has been tested and what the numbers were. Read before
   proposing an analysis, so you do not re-run something already answered or
   contradict a measured result.
3. `DATA_DICTIONARY.md` — every column, its units, and what will burn you. Read
   before touching any column. Generated from `schema.yaml`; edit the YAML.

Add to `FINDINGS.md` whenever an analysis produces a number worth keeping, and to
`DECISIONS.md` whenever a choice is made that a future reader would otherwise
have to reconstruct. Append; do not rewrite history.


## GitHub and Savant are both unreachable from the sandbox

`git push` fails with `502 from proxy after CONNECT`, and Savant with a 403.
Both are the session egress allowlist, not the remote. Pushing and fetching are
run by the user in their own Terminal. Adding a host to the allowlist mid-session
does not help — egress policy is snapshotted when a session starts, so the change
only reaches the next one.

`~/.claude` is a protected location the bridge refuses to connect at all, so
anything under it is the user's to run.

## Never run git from the Cowork sandbox

The sandbox shell cannot delete files. `git add` creates `.git/index.lock` and
then cannot remove it, which leaves the repo locked for the user with a
confusing "another git process seems to be running" error that has nothing to do
with any running process. It has happened once; the fix is
`rm -f .git/index.lock` from the user's own Terminal.

**Claude edits files here; the user runs every git command.** When a change is
ready, say so and let the user stage and commit it.

## SQLite lives on a mounted volume

`data/statcast.db` is on a folder mounted into the sandbox. Long or concurrent
reads against it fail with `sqlite3.OperationalError: disk I/O error` — this is
the mount, not corruption. Copy the database to sandbox-local scratch first and
point the tool at the copy:

    cp data/statcast.db $HOME/snap.db
    python3 audit.py --db $HOME/snap.db

Never write a database back from scratch into the repo; re-run the pipeline on
the user's machine instead.

## Baseball Savant is not reachable from the sandbox

Anything that fetches (`backfill.py`, `run_pipeline.py`, `refresh.sh`) runs in
the user's own Terminal. Everything that only reads the database — `audit.py`,
`report.py`, `make_dictionary.py`, `selftest.py` — runs fine in the sandbox.

## schema.yaml is the source of truth

`DATA_DICTIONARY.md` is generated by `make_dictionary.py`; editing the markdown
loses the change on the next build. `audit.py` reads applicability conditions
and plausible ranges from the same YAML, so a fact is stated once and reaches
both the checks and the docs.

Adding a column means adding a `schema.yaml` entry. The audit fails on any
database column that has no entry, which is deliberate: Savant widens the table
mid-season and an undocumented column is a metric nobody has decided how to
treat.

## Never write to the database through the mount

Reading `data/statcast.db` from the sandbox is fine. WRITING to it is not — a
`CREATE INDEX` issued from the sandbox failed mid-write with `disk I/O error`
and left the 1.8 GB file structurally corrupt (`quick_check` reported
out-of-order rowids and doubly-referenced pages). The damage is silent: counts
and most queries still work.

Any statement that writes — `CREATE INDEX`, `VACUUM`, `PRAGMA` that persists,
`INSERT`, `DELETE` — runs on the Mac. From the sandbox, open read-only and
accept the slower query plan:

    sqlite3.connect("file:data/statcast.db?mode=ro", uri=True)

Recovery, if it happens again: `sqlite3 db ".recover" | sqlite3 new.db`, then
`verify_recovery.py --fix` to queue damaged days, then `backfill.py`.


## The repo must not live in ~/Desktop

macOS TCC protects ~/Desktop, ~/Documents and ~/Downloads. A script run by
launchd executes as /bin/bash, which has no access to those folders, so the
scheduled refresh failed with:

    /bin/bash: .../refresh.sh: Operation not permitted

and produced an empty refresh.log, because the script never started. Running the
same script by hand works, because Terminal has been granted access and the
script inherits it. That asymmetry is what makes this so confusing to diagnose.

The repo therefore lives in ~/Projects/statcast-dashboard, which TCC does not
protect. The launchd plist hard-codes that path. Do not move the repo back into
a protected folder, and do not "fix" this by granting Full Disk Access to
/bin/bash -- that hands unrestricted disk access to every shell script on the
machine, forever.
